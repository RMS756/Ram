Tool-using agents built on large language models can now initiate payments, change account details and send data to external recipients. Indirect prompt injection, content placed in a tool output or a retrieved document that the agent then follows, can make such an agent propose a financial action that serves an attacker rather than the user.

This thesis designs, implements and evaluates the Runtime Evaluation and Mitigation (REM) framework, a five-layer runtime layer placed at the tool-execution boundary. For each proposed tool call, REM estimates the probability that the call was adversarially induced, using ridge logistic regression calibrated on the logit; assigns a declared consequence tier; applies policy predicates; selects one of four verdicts (Allow, Modify, Escalate or Block) by minimizing expected loss under tier-indexed costs; and records every verdict for audit. Every constituent mechanism is established in prior work, and closely related designs have been published. The thesis therefore asks an evidence question: does a learned, consequence-aware runtime decision add value over simple provenance and authorization rules for a banking agent when the user task and the attack objective are unseen, and at what cost in legitimate work?

REM was evaluated on recorded trajectories of real agents in the AgentDojo banking environment by recorded-trace replay, which assumes that the agent does not adapt to a refusal. On 3,313 episodes, with whole attack objectives held out from fitting, the estimator separated attack attempts from legitimate calls (ROC-AUC 0.938), and REM reduced attack success from 22.6% to 0.4%. It did so largely by withholding state-changing calls: benign task completion fell from 52% to 31%, and only 33 of 178 legitimate state-changing calls were released. Rules that use one or two pieces of provenance evidence and no model reached the same security with 40–42% benign task completion; one of them failed when the attacker's account number was reformatted. REM's attack count and benign task count were the same when the user task was also held out. A pre-declared candidate that added authorization evidence and was trained on intervention outcomes was rejected (132 successful attacks against 11), because it did not transfer to an unseen attack objective. Removing calibration left the attack count unchanged and changed five benign outcomes, and Modify, Escalate and Block had identical effect. A final ablation committed before scoring confirmed, with paired intervals, that the learned decision prevents 661 of the 672 attacks that REM stops and admits none, at a cost of 22.5 percentage points of benign task completion, and that calibration and Modify change no attack outcome. A layer-wise ablation on three populations found that every outcome effect comes from that decision acting through enforcement (in shadow mode the same verdicts protected nothing), that removing the action/provenance evidence let more attack calls execute, and that the Detection layer's instruction-pattern indicator and the policy predicates had no measurable effect; the Input & Context layer could not be removed on its own. On the same task pairs, REM's replayed decisions left fewer successful attacks than the recorded runs of three of the four defenses distributed with the benchmark and about as many as its injection classifier, with lower benign task completion; this comparison is descriptive, because the defenses' runs are closed-loop and REM's is a replay. Progent's published banking policy, decided by Progent's own enforcement code on the same recorded episodes, admitted no attack and completed more tasks under attack than REM on all three populations; its list of permitted recipients contains values specific to the benchmark. DRIFT and MELON, which need a language model, were compared at the level of architecture and code only.

One modification was tested under a protocol committed before its data were opened: removing the behavioral evidence group. On 2,113 recorded episodes that no analysis had read before that run, it raised task completion by 7.5 percentage points (95% interval 1.2 to 16.0) with 1 successful attack against 3 of 2,065, meeting the pre-declared decision rule; the security difference is not resolved statistically. It is proposed as a versioned amendment (REM v1.1) pending the supervisor's approval; the original specification remains the baseline. Neither version was distinguishable from the simple rules. On paired test cases, none of these policies, learned or rule-based, separated an authorized payment from an unrequested one whose details appear in the user's own words.

An exploratory extension then compiled the user's request into instructions with a deterministic parser and released a state-changing call only if it matched one of them in operation, recipient, amount and stated condition. Two external reviews found defects in the matching; each repair was frozen before it was scored. On development data the current rule had no successful attack on either population and completed 132 of 334 benign tasks, against 105 for REM v1.0. Against the strongest simple rule it had fewer successful attacks (0 against 13 and 0 against 4), while the difference in completed tasks was not resolved. A fixed-list policy from Progent's repository (a manual banking policy), replayed in the same harness, also had no successful attack. The rule's authority guard used alone (GV) completed 147 benign tasks. Behind that guard, a learned model, statistically calibrated thresholds and gradient-boosted trees gave exactly GV's outcomes, except one threshold that lost tasks, because every attack-labelled call was stopped before any of them was consulted. The measured change is therefore attributed to deterministic components, not to the learned core. A later review found that the guard accepted computed amounts it never computed ("half of 100") and read a percentage coefficient as the amount. A typed verifier with exact arithmetic repaired both with no successful attack, at a cost of 95 and 159 completed tasks whose amounts the request does not determine; the learned decision behind it again changed nothing. A second review found that this verifier still accepted a supported part of a compound calculation and an amount taken from an instruction whose condition did not hold; a second version repaired both on the diagnostic cases without changing any recorded outcome, and withheld one further legitimate test case. Published preprints apply closely related request-derived argument checks. All of these security differences arise in one benchmark task, and a validation on independently written requests was defined but not executed.

The results are exploratory and come from replay, not from live agents; a closed-loop harness and integrations with the MELON and DRIFT defenses are implemented and were not executed with a language model. Within the methods tested, the results give priority to improving how the user's request is represented over improving the estimator; they do not rule out a benefit from estimators or verification mechanisms that were not tested.
