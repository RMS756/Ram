Tool-using agents built on large language models can now initiate payments, change account details and send data to external recipients. Indirect prompt injection, content placed in a tool output or a retrieved document that the agent then follows, can make such an agent propose a financial action that serves an attacker rather than the user.

This thesis designs, implements and evaluates the Runtime Evaluation and Mitigation (REM) framework, a five-layer runtime layer placed at the tool-execution boundary. For each proposed tool call, REM estimates the probability that the call was adversarially induced, using ridge logistic regression calibrated on the logit; assigns a declared consequence tier; applies policy predicates; selects one of four verdicts (Allow, Modify, Escalate or Block) by minimizing expected loss under tier-indexed costs; and records every verdict for audit. Every constituent mechanism is established in prior work, and closely related designs have been published. The thesis therefore asks an evidence question: does a learned, consequence-aware runtime decision add value over simple provenance and authorization rules for a banking agent when the user task and the attack objective are unseen, and at what cost in legitimate work?

REM was evaluated on recorded trajectories of real agents in the AgentDojo banking environment by recorded-trace replay, which assumes that the agent does not adapt to a refusal. On 3,313 episodes, with whole attack objectives held out from fitting, the estimator separated attack attempts from legitimate calls (ROC-AUC 0.938), and REM reduced attack success from 22.6% to 0.4%. It did so largely by withholding state-changing calls: benign task completion fell from 52% to 31%, and only 33 of 178 legitimate state-changing calls were released. Rules that use one or two pieces of provenance evidence and no model reached the same security with 40–42% benign task completion; one of them failed when the attacker's account number was reformatted. REM's attack count and benign task count were the same when the user task was also held out. A pre-declared candidate that added authorization evidence and was trained on intervention outcomes was rejected (132 successful attacks against 11), because it did not transfer to an unseen attack objective. Removing calibration left the attack count unchanged and changed five benign outcomes, and Modify, Escalate and Block had identical effect.

One modification was tested under a protocol committed before its data were opened: removing the behavioral evidence group. On 2,113 recorded episodes that no analysis had read before that run, it raised task completion by 7.5 percentage points (95% interval 1.2 to 16.0) with 1 successful attack against 3 of 2,065, meeting the pre-declared decision rule; the security difference is not resolved statistically. It is proposed as a versioned amendment (REM v1.1) pending the supervisor's approval; the original specification remains the baseline. Neither version was distinguishable from the simple rules. On paired test cases, none of these policies, learned or rule-based, separated an authorized payment from an unrequested one whose details appear in the user's own words.

An exploratory extension then compiled the user's request into task-permission evidence with a deterministic parser and matched each state-changing call on operation, recipient and amount. On development data this rule completed more benign tasks than REM (149 against 105 of 334) with no more successful attacks (10 against 11). Its advantage over the strongest simple rule was not statistically resolved; a published fixed-list policy (the manual banking policy of Progent), replayed in the same harness, had no successful attack; and a learned model on the same evidence added no demonstrated value and was less robust to reformatted identifiers. The gain is therefore attributed to the deterministic rule, not to the learned core.

The results are exploratory and come from replay, not from live agents; a closed-loop harness and an integration with the MELON defense are implemented and were not executed with a language model. Their main implication is that, at the tool boundary, what limits a monitor is whether its evidence represents what the user asked for and authorized, not the estimator.

**Keywords:** AI agent security; indirect prompt injection; runtime monitoring; financial AI agents; tool-use security; authorization; provenance; expected-loss decision; AgentDojo.
