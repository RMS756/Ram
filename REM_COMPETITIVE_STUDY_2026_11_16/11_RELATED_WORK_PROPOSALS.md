## 3. What was executed

Protocol: `PROTOCOL_ADDENDUM_SECTION11.md`. Results: `03_RESULTS_TABLES.md`, Table 13; `results/results_section11.json`.

### 3.1 Cedar front (GVc): a policy-engine implementation study

- **Representation.** Principal `User::"account_holder"`; action = the tool; resource = the account; context = eight typed fields that REM computes (authority, permission status, effect, binding, condition, fulfilment, direct-value outcome, declared predicate). One permit and eight forbids (`experiments/competitive_study/cedar_front.py`). The remaining execution allowance is the *fulfilment* field: REM counts executed payments (only a successful execution counts) and passes the result; Cedar keeps no history.
- **Validation and failure handling.** Policies are validated against a schema when the module loads; an invalid policy set makes the module unusable. Each request is validated against the schema. The wrapper releases only on an Allow with no reported error. This is this study's choice: Cedar itself skips an erroring policy, and a test shows a case where Cedar answers Allow with an error and the wrapper withholds.
- **Result.** 8,106 replays, 7,098 restricted calls: 2,833 Allow, 4,265 Deny, 0 errors, **0 differences from GV**; fixtures 36 / 0 / 36, identical. Median 2.33 ms per restricted call.
- **What it supports.** Cedar can host these constraints with decision parity on the supported cases. It supports no claim of better security or utility, and no claim about policy expansion.

### 3.2 Provenance rule (GVp): an additional-enforcement study

- **Audit of what the recordings expose.** Trust labels come from message roles (harness instrumentation); untrusted text cannot label itself trusted. Origin of a value is known only by typed matching of the call's key arguments against trusted and untrusted text. Data flow through the model is not recorded. Where no key argument is present the indicator is unavailable (55 and 62 calls), and that is reported, not imputed.
- **Policy.** Authority (operation, effect, account, credential) comes from the request only: unchanged front. Data may come from external content inside a workflow the request authorizes: a value the request confirms or delegates is released as before ("pay this invoice" style requests are not blocked). A value that the request neither confirms nor delegates, and that occurs in untrusted content only, is withheld.
- **Result.** No attack removed (none reaches the rule); 27 and 6 legitimate calls withheld; 1,530 against 1,532 and 1,389 against 1,386 tasks; fixtures unchanged. Not a demonstrated benefit and not a demonstrated harm.
- **Learner's increment with the same input.** HV's model already receives the provenance indicators; its outcomes equal GV's. The differences among GV, GVp and HV are those few episodes. No improvement is attributed to a learner.

## 4. Review path: specification only (not implemented, not evaluated)

If a reviewer is ever studied: the reviewer sees the user's request, the proposed tool, account, amount, the condition and its evaluation, and how many executions of that instruction remain. An approval is a record `(episode, instruction, tool, canonical account, exact amount, one execution)`; it is consumed by one successful execution of exactly that call and authorizes nothing else. A changed call needs a new approval. Without a real reviewer, escalation withholds and costs utility; a simulated reviewer must be reported as simulated and an ideal reviewer only as an upper bound.

## 5. What goes where in the thesis

Chapter 2 may mention Cedar, FIDES and CaMeL selectively, at the verification level stated in Section 1, tied to the financial runtime threat model. Only GVc and GVp are executed experiments, both exploratory. Nothing here supports "first hybrid defense", novelty for financial agents, or superiority over Progent.
